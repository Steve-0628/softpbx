# 04. ファックスの設計

## 1. 対応する 4 つの形

| # | 形 | 経路 | 用途 |
| --- | --- | --- | --- |
| 1 | T.38 中継 | IP ↔ IP | 拠点間（宅外 PBX）や T.38 対応ゲートウェイとの FAX |
| 2 | G.711 パススルー | IP ↔ IP | T.38 非対応の相手へのフォールバック |
| 3 | アナログ FAX 機接続 | アナログ FAX 機 ↔ IP | 既存の実機をそのまま使う（ゲートウェイ FXS 経由） |
| 4 | ファックスサーバ | 受信 → PDF/メール、送信 → PDF/TIFF | 紙を使わない FAX 送受信 |

1〜3 は **FAX 信号の透過伝送**、4 は **FAX を終端してイメージ化**する。実装上は別の系。

## 2. T.38 中継（ゲートウェイ）

T.30（FAX 手順）の信号を T.38 の UDPTL へ変換する。両側が T.38 なら中継、
片側が G.711/アナログならゲートウェイとして振る舞う。

```
[FAX端末A] --T.30-- [softpbx] --T.38/UDPTL-- [相手 PBX / GW] --T.30-- [FAX端末B]
```

- **negotiation**: SDP の `m=image` / `a=T38FaxVersion` で能力を交換。
  交渉できない場合は G.711 パススルーへフォールバック（re-INVITE）。
- **UDPTL 冗長化**: パケットロス対策に redundancy / FEC を使用。経路特性に応じて選択。
- **対応モデム方式**: V.21（手順信号）、V.29、V.17（7200〜14400bps）。
  **V.34（T.38 Annex E）は v1 では対象外**（必要になったら追加）。
- **ECM（誤り訂正モード）**: 対応する。非対応相手へのフォールバックも実装。
- T.38 は「遅延に強いが、欠損に弱い」。パケット周期は UDPTL の冗長化設定と
  整合させる（通常 100〜400ms 単位のバケット）。

## 3. G.711 パススルー

T.38 が使えない場合のフォールバック。**FAX 信号を壊さないことだけを優先**する。

- コーデックは G.711 固定（µ/A は相手に合わせる）、ptime は 10ms を基本
- VBD モード（docs/03 §4）を必ず適用:
  - エコー除去・VAD・DTX・CNG・PLC・AGC・DTMF 検出を停止
  - ジッタバッファを固定、欠損を復元しない
- 相手が対応するなら `a=ptime:10` と `a=silenceSupp:off` を送る
- パススルーは LAN 内（または低ジッタ経路）では十分成立するが、
  **インターネット経路では成功率が下がる**。拠点間は T.38 を優先する。

## 4. アナログ FAX 機の接続

ゲートウェイの FXS ポートに実機を接続し、内線として登録する。
FAX 機は通常の電話機と同様に着信し、発信する。

- 発信時：FAX 機のダイヤル → ゲートウェイ経由で SIP 発信 → softpbx がルーティング
- 着信時：softpbx から SIP 着信 → ゲートウェイが着信信号（16〜25Hz 相当）を発生 → FAX 機応答
- 信号は G.711 または T.38 で中継（ゲートウェイの対応に依存）
- **注意**: ゲートウェイが FAX 音声から自動的に T.38 へ切り替える機種と、
  常に G.711 で通す機種がある。機種プロファイル（`line-gw`）で分ける。

## 5. ファックスサーバ

FAX を終端してイメージ化する系。T.37 の考え方（store-and-forward）に近い。

### 5.1 受信

```
FAX 信号 → [T.30 終端] → T.4/T.6 デコード → TIFF(G3/G4) → PDF 変換 → メール添付送信
                                      └→ 保存（inbox/）+ 結果通知
```

- T.30 を自前で終端する（`t38` クレートと T.30 実装を共有）
- 保存形式は TIFF（Fax G3/G4）を正とし、PDF を派生として生成
- メール送信は SMTP（`lettre`）。失敗時はスプールに残し指数バックオフで再送
- 受信完了・失敗を WebSocket イベントとログに記録

### 5.2 送信

```
PDF/TIFF → ページ変換 → T.4/T.6 符号化 → [T.30 終端] → T.38 / G.711 / アナログ
                                              └→ 結果（成功/失敗/ページ数）を記録
```

- 入力: PDF、TIFF（Fax G3/G4）
- 送信先の能力（解像度、ECM、V.17 対応）は T.30 の交渉に従う
- スプール（`fax/spool/`）で送信キューを管理し、同時送信数を制限
- 失敗理由（相手応答なし、ページ不一致、交渉失敗）を記録して再送可否を判断

### 5.3 実装上の注意

| 項目 | 内容 |
| --- | --- |
| イメージ処理 | T.4（MH/MMR）/ T.6（MMR）の符号化・復号が必要。純 Rust 実装（`fax` 系クレート）または FFI |
| PDF 生成 | ファックス用の 1bit イメージ埋め込み PDF で十分（検索性は不要なら OCR なし） |
| メモリ | 1 ページあたりのバッファを固定長で管理し、大型 FAX でメモリを食い潰さない |
| 時刻・送信元 | T.30 の CSI/TSI、日時の取り扱いを明確にする（ログと密接に関わる） |
| 拠点間 | 相手が MikoPBX/ Asterisk の場合、T.38 の交渉順序や re-INVITE のタイミングが異なる。相互接続テストで確認 |

## 6. テストの考え方（詳細は docs/06）

- `engine-sim` に**疑似 FAX 機（T.30 状態機械）**を実装し、決定的に送受信を再現する
- V.17 / V.29 / V.21 の各速度、ECM 有無、ロス 0/0.1/1% の条件で合格判定
- 実機（主要メーカーの FAX 機）との相互接続マトリクスを別途持つ
