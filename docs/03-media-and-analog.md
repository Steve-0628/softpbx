# 03. メディア面とアナログ端末の設計

## 1. メディアパイプライン

```
RTP 受信 → [ジッタバッファ] → [復号] → [DSP] → [符号化] → RTP 送信
              │                 │        │
              │                 │        └ VBD 検出・モード切替 / エコー除去 / ミキサ
              │                 └ コーデック（G.711 / G.722 / Opus）
              └ 音声: 適応型（20〜80ms） / VBD: 固定（厳格）
```

- メディア面は**専用スレッド**で、起動時にバッファをすべて確保する。
- パケット処理の予算は **1 パケットあたり < 1ms**（10ms 周期で 10% 以下）。
- 1 通話 = 2 レグ（B2BUA）。両レグでコーデック・ptime・SRTP を個別に交渉する。
  **同一コーデックなら可能な限りトランスコードしない**（遅延と CPU を節約し、
  FAX/モデムの劣化を防ぐ）。

## 2. ジッタバッファ

| 用途 | 方式 | 初期値の目安 |
| --- | --- | --- |
| 通常音声 | 適応型（遅延と欠損のトレードオフを自動調整） | 20〜80ms |
| VBD（FAX/モデム） | **固定**（適応を止め、欠損リカバリも行わない） | パケット周期 + 1 〜 2 パケット |
| 会議 | 適応型 + 合成時の位相合わせ | 40ms 程度 |

VBD で適応型を使わないのは、**バッファ長の変化自体がモデム/FAX 信号の
タイミングを壊す**ため。この切替は `vbd` クレートが `media` へ指示する（§4）。

## 3. DSP

- **コーデック**: G.711（µ/A、純 Rust で十分）、G.722、Opus（`libopus` FFI）。
  G.729 は必要になった時点で。
- **エコー除去（G.168 相当）**: アナログ端末経由の通話で必要。**VBD モードでは必ず停止**。
- **ミキサ（会議）**: 整数演算の固定小数点ミキサを基本とし、飽積防止を必ず入れる。
- **DTMF**: RFC 4733（RTP イベント）を優先、次いで帯域内検出（Goertzel）、
  SIP INFO。3 方式を併用できるが、**VBD 中は検出を停止**する。
- 使ってはいけない処理（VBD 中）: VAD / DTX / 快適雑音（RFC 3389）/ パケットロス
  補間（PLC）/ AGC / ビットレート可変

## 4. VBD（音声帯域データ）モード

FAX・モデムを検出した時点で通話全体を**データ伝送モード**へ切り替える。
ここが本ソフトウェアの技術的な要であり、誤ると FAX/モデムが必ず失敗する。

### 4.1 検出

| 対象 | 手がかり |
| --- | --- |
| FAX | CNG（1100Hz 断続）、CED、V.21 プリアンブル（T.30）、V.8 CM/JM |
| モデム | V.8 CM/JM、V.25 ANS/ANSam、キャリアトーン |
| 3.1kHz データ | 指示（発信側の設定）または上記の検出 |

検出は `vbd` クレート（帯域内のトーン解析 + RFC 4734 の RTP イベント）が行い、
必要に応じて **re-INVITE によるコーデック変更（G.711 固定・ptime 短縮）**を
制御面へ要求する。

### 4.2 モード遷移（FSM）

```
Voice ──検出──> VbdEnter ──re-INVITE 完了──> VbdActive ──終了──> VbdExit ──> Voice
```

- `VbdEnter` で: エコー除去・VAD・DTX・CNG・PLC・AGC・DTMF 検出を停止し、
  ジッタバッファを固定へ、ptime を 10ms へ変更（相手が許容する範囲で）。
- `VbdActive` では**再 INVITE を行わない**（メッセージ列の乱れを防ぐ）。
- 終了検出はキャリア消失 + タイムアウトで行い、元の音声設定へ復帰する。

### 4.3 パケットの扱い

- 欠損は**復元しない**（PLC は信号を歪める）。欠損はそのまま欠損として渡す。
- SRTP は VBD でも有効にできるが、**暗号化による遅延変動が出ない方式**を選ぶ。
- 送信はパケット周期を厳密に保つ（バースト送信・遅延送信をしない）。

## 5. アナログ端末の扱い（外付けゲートウェイ経由）

アナログ端末（電話機・FAX 機・モデム）は**外付けゲートウェイ（Yamaha NVR500/510 級）**
に接続され、本ソフトウェアからは **SIP 端末として見える**。

```
[アナログ電話機] ──FXS── [ゲートウェイ] ──SIP/RTP── [softpbx]
[アナログFAX 機] ──FXS── [     〃      ] ──T.38/G.711─ [  〃  ]
[アナログモデム] ──FXS── [     〃      ] ──G.711────── [  〃  ]
```

- 本ソフトウェアは**TDM クロックもライン電圧も直接制御できない**。
  制御できるのは SIP/RTP 側の挙動と、ゲートウェイの設定配信のみ。
- したがって `line-gw` クレートは次の 2 つを担う。
  1. **ゲートウェイのプロビジョニング**（設定生成・配信・状態監視）
  2. **ゲートウェイ特性プロファイル**（クイーク層）：ptime、DTMF 方式、
     T.38 対応、FSK 発信者番号通知の扱い、SDP の癖などを機種別データで保持

### ゲートウェイ経由でできること / できないこと

| 項目 | 可否 | 備考 |
| --- | --- | --- |
| 通話（音声） | ◎ | 通常運用で問題になりにくい |
| 発信者番号通知 | ○ | 機種が FSK を RTP 上でどう扱うかに依存 |
| FAX（G.711） | ○ | パケット周期とバッファ設定に依存 |
| FAX（T.38） | ○〜△ | ゲートウェイの T.38 対応に依存（検証必須） |
| モデム伝送 | △〜✕ | **最大のリスク。実機検証なしに確約できない** |

## 6. ゲートウェイ確定時の検証項目

機種（NVR500/510 級）確定後、次の表を作り切る（docs/06 の相互運用テスト）。

1. T.38 中継の対応有無、UDPTL 冗長化（redundancy / FEC）の挙動
2. G.711 パススルー時の ptime、ジッタバッファの固定可否、VAD の既定値
3. DTMF の通知方式（RFC 4733 / 帯域内 / SIP INFO）と併用時の挙動
4. 発信者番号通知（FSK）の伝送方法と、通知タイミング
5. FAX/モデム検出時に re-INVITE を送るか、送る場合の順序
6. 設定配信方式（HTTP / TFTP / 独自 API）と再起動・再読込の振る舞い
7. 電源断・LAN 断からの復旧時間、通話の維持可否

## 7. QoS とパケット処理

- 音声: DSCP EF（46）、FAX/モデム: 音声と同じく EF（欠損に弱いため最優先）
- 送信は `sendmmsg` 等でまとめて送らず**周期を優先**する（バッチよりジッタ抑制）
- 受信は `recvmmsg` + ソケットバッファの十分な確保。オーバーフロー時は
  統計を取り、閾値超過でアラート（通話中の処理ではログを出さない）
- VM 運用時は vCPU のピニングとノンノイズなホストを推奨（ゲートウェイ経由でも
  PBX 側のジッタは FAX/モデムに影響する）
